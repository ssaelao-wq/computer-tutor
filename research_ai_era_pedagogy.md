# How Others Teach Programming in the AI Era — Research, Analysis, and a Proposed Structure

**Purpose:** The teacher judged the current platform structure inefficient and asked for research into how other platforms and researchers approach programming education in the AI era, plus a recommended approach. This document is research + analysis + proposal only — **nothing here has been implemented.**

**Date:** 2026-07-30

---

## Part 1 — What the research actually says

### 1.1 The single most important finding: AI widens the gap, it doesn't lift everyone

The most directly relevant study is *"The Widening Gap: The Benefits and Harms of Generative AI for Novice Programmers"* ([arXiv](https://arxiv.org/html/2405.17739v1)). Its findings should shape everything:

- Struggling students accepted AI suggestions **34.1%** of the time vs **24.5%** for successful students. More acceptance correlated with *worse* outcomes.
- Struggling students finished with an **"illusion of competence"** — in post-interviews they rationalised their process in ways that directly contradicted their observed behaviour. They believed they understood far more than they demonstrated.
- Two named failure modes:
  - **Shepherding** — over-reliance; the student rarely writes any code of their own.
  - **Drifting** — bouncing between AI suggestions, making no actual progress.
- What distinguished the students who *benefited*: they had **"negative expertise"** — they could quickly recognise *bad* AI output. They verbalised the problem before implementing, and selectively accepted suggestions after evaluating them.
- Three new metacognitive difficulties unique to AI use: **interruption** (suggestions break concentration), **mislead** (steered into wrong solutions they can't escape), **progression** (falling behind while feeling confident).

**Implication:** the goal of an AI-era curriculum is not "teach them to use AI." It is **to manufacture negative expertise** — the ability to look at plausible-looking generated code and know it's wrong. That is a *reading* and *predicting* skill, not a prompting skill.

### 1.2 PRIMM — the most validated structure for novice programming

**PRIMM** = Predict → Run → Investigate → Modify → Make ([Raspberry Pi Foundation PDF](https://www.raspberrypi.org/app/uploads/2022/08/Teaching_Programming_with_PRIMM-1.pdf), [Teach Computing](https://teachcomputing.org/blog/using-primm-to-structure-programming-lessons/), [ACM](https://dl.acm.org/doi/10.1145/3287324.3287477)).

- Built on three research bases: **Use-Modify-Create**, **Levels of Abstraction**, and **code tracing/comprehension research**.
- Core principle: **reading before writing.** Students read and understand existing code *before* producing their own.
- Measured result: learners performed better on post-tests than a control group. Teachers reported it works especially well in **mixed-ability** settings — everyone makes progress.
- In use as a standard structure since 2017.

**The critical detail: "Predict" comes first, before "Run."** The student commits to a prediction *before* seeing what the code does. That commitment is where the learning happens — it exposes the gap between what they think they know and what's true.

### 1.3 Prompt Problems — the closest published work to what this platform is doing

*"Prompt Problems: A New Programming Exercise for the Generative AI Era"* and *"Promptly"* (Denny, Leinonen, Prather, Smith, MacNeil, Becker, Luxton-Reilly et al.) — [arXiv 2311.05943](https://arxiv.org/abs/2311.05943), [arXiv 2401.10759](https://arxiv.org/abs/2401.10759), [arXiv 2307.16364](https://arxiv.org/abs/2307.16364).

- Students are shown a computational task **visually — deliberately with no textual description** — and must write a natural-language prompt that makes an LLM produce code solving it.
- **How it's graded — this is the key design decision:** *"The problem is considered correct when the code that is generated by the student prompt can pass all test cases."*

**Why the visual presentation matters:** if you describe the task in words, the student can copy your words into the prompt. Removing the text forces the student to do the actual work — translating an understood goal into precise language. That is the skill being taught.

**Why test-case grading matters:** the prompt is judged by *whether it produced working software*, not by anyone's opinion of the prompt. Objective, non-gameable, and it's the same feedback loop professionals actually have.

### 1.4 Which engagement techniques actually work with AI-generated code

*"Exploring the Design Space of Cognitive Engagement Techniques with AI-Generated Code"* (Kazemitabaar et al., IUI 2025) — [arXiv](https://arxiv.org/abs/2410.08922), [project page](https://majeedkazemi.github.io/code-engagement-techniques/), [summary](https://kamibrumi.medium.com/how-to-keep-students-engaged-when-ai-can-do-their-programming-homework-0629a5da868e).

Seven/eight techniques were designed and tested against a baseline (AI generates code + explanation, minimal engagement required). Studies with N=82 then N=42. Two clear winners:

- **Lead-and-Reveal** — the student predicts each line through scaffolded questions; the code is revealed progressively based on their answers. *Best overall: strong learning gains with low friction.* Notably improved students' **self-awareness** and independent problem-solving.
- **Trace-and-Predict** — the student predicts variable states and control flow, simulating debugging. *Deeper comprehension but higher cognitive cost and slower.*

Both substantially beat the baseline on **transfer to isomorphic tasks without AI assistance** — i.e. could they then do it themselves. The paper explicitly measured "success in aligning learners' perceived and actual coding abilities" — directly targeting the illusion-of-competence problem.

**Implication:** "here's the AI's code, now explain it" (the current platform's Explain box) is close to the *baseline* condition that lost. Explanation *after* seeing working code is post-hoc rationalisation. Prediction *before* the reveal is what produced transfer.

### 1.5 What university CS is actually changing

*"Reshaping Undergraduate Computer Science Education in the Generative AI Era"* — [arXiv](https://arxiv.org/html/2606.07545), plus the [GenAI in CS Education Consortium](https://www.teachcswithai.org/home).

- **Preserve:** abstraction, verification, system design, code review, problem specification, "taking responsibility for systems."
- **Deprioritise:** low-level syntax memorisation, rote coding mechanics, boilerplate.
- **New priorities:** specification writing, verification of AI-generated code, metacognition and self-regulation.
- **Concrete assessment change:** have students *"submit specifications, tests, or formal properties alongside code."*
- **Reverse-engineering exercises:** students extract the specification *from* a completed solution.
- **Dual assessment:** controlled AI-free testing *alongside* open AI-allowed assignments.
- Sobering note from the same literature: *"students rarely engage in deep cognitive strategies (e.g. reflection, evaluation) when working with GenAI"* unless the tooling forces it.

### 1.6 Cognitive load: Parsons problems and faded worked examples

([Koli Calling](https://dl.acm.org/doi/10.1145/3769994.3770032), [ICER 2024](https://dl.acm.org/doi/10.1145/3632620.3671110), [arXiv](https://arxiv.org/pdf/2311.18115))

- **Parsons problems** (reorder scrambled correct lines) produce equivalent learning to writing code from scratch, in **significantly less time**, with **significantly lower cognitive load**.
- Especially effective for students with **low self-efficacy** — exactly the students AI harms most.
- **Faded worked examples + metacognitive scaffolding** was found most effective for problem-solving and self-regulation.
- Crucially: **scaffolding must fade as expertise develops.** Constant scaffolding stops helping.

### 1.7 What commercial platforms do

- **Scrimba** — interactive screencasts where the video *is* the editor; pause any moment and edit the instructor's code in place. Removes all context-switching friction.
- **Boot.dev** — read a concept → write code → instant automated feedback, with RPG-style XP progression. Tight, objective feedback loops.
- **Exercism** — automated tests plus **human mentor review** focused on making solutions *idiomatic*, not just correct.

Common thread across all three: **fast, objective, automated feedback on whether the thing actually works** — with human judgment reserved for quality and style, not correctness.

## Part 2 — What this says about the current platform

Reading the current L1 design against this evidence, seven structural problems stand out. Ordered by how much they matter.

**1. There is no objective ground truth anywhere in the system.**
Every exercise is graded by an LLM's opinion — first of understanding, now of prompt quality. Promptly, Boot.dev, and Exercism all anchor on *does the code actually pass tests*. The platform already has both halves needed for this (`/api/generate-code` and a live sandbox that runs code), but no test cases. This is the largest single gap and the root of the "grading feels arbitrary" frustration that has recurred throughout this project.

**2. Explanation happens after the reveal, so it measures rationalisation, not understanding.**
The current flow is Plan → Prompt → paste working code → *then* explain. By the time the student explains, they've already seen it work. This is structurally the baseline condition that lost in the Kazemitabaar study, and it's the mechanism that produces illusion of competence. **There is no prediction step anywhere in the platform.**

**3. Students never read code they didn't cause to be written.**
PRIMM's entire foundation is reading before writing. In the current design, every piece of code a student sees is code their own prompt produced. They never practise the actual professional skill — being handed unfamiliar code and figuring out what it does. Negative expertise cannot develop this way.

**4. No verification artifact is ever produced.**
Test & Break was removed from the UI (correctly — a "did you try to break it?" textbox is hollow). But the research recommendation isn't a reflection box, it's *"submit tests alongside code."* A written test case is objective, checkable, and impossible to fake by writing a nice paragraph. The baby went out with the bathwater.

**5. Scaffolding never fades.**
Session 1 and Session 12 have an identical box structure, identical support level, identical everything. Research is explicit that scaffolding must fade. A student who has done this twelve times is being propped up exactly as much as on day one — which is precisely why they can't build independently at the end.

**6. One modality for everything.**
Every exercise in all twelve sessions is the same 3–4 box shape. Different techniques serve different purposes: Parsons for early low-cognitive-load practice, trace-and-predict for comprehension, prompt problems for specification skills, free build for transfer. Using one shape for all of it means most exercises are the wrong tool for their job.

**7. Construct-by-construct sequencing** (already diagnosed in `improve_concept.md` — variables week, events week, conditionals week — rather than capability-driven).

## Part 3 — Proposed structure

### 3.1 The core idea

Replace the uniform 4-box exercise with **four distinct exercise modes**, mapped onto PRIMM, with **objective grading wherever possible** and **deliberate fading across the level**.

| Mode | PRIMM stage | What the student does | How it's graded | LLM needed? |
|---|---|---|---|---|
| **1. Predict** | Predict + Run + Investigate | Given working game code they didn't write, predict what it does / what variables hold, *then* run it and compare | Prediction vs. actual output — exact match | **No** |
| **2. Modify** | Modify | Given working code + a changed requirement, make a small bounded change (Parsons variant available for strugglers) | Run it; assert the behaviour changed as specified | **No** |
| **3. Specify** | (AI-era addition) | Shown the goal **visually** — a short clip of the car doing the thing, no text description — write a prompt that makes AI produce code achieving it | **Generate code from their prompt, run it against test cases** | Yes (already built) |
| **4. Make** | Make | Extend their own accumulating `game.js` with the capability — **and write the test cases first** | Teacher-reviewed + their own tests must pass | Optional |

### 3.2 Why each mode earns its place

- **Predict** is the missing foundation. It's where negative expertise comes from, it's auto-gradeable at zero LLM cost, and it directly attacks illusion of competence by forcing a commitment before the reveal. Variant worth using: *reverse-engineering* — show finished code, ask the student to write the specification it satisfies.
- **Modify** is the safest possible bridge to authorship — bounded, low cognitive load, and per the Parsons research, equally effective and faster than writing from scratch. Offer the Parsons (reorder scrambled lines) version as the fallback for students who stall.
- **Specify** is the current platform's prompt work, fixed. Two changes make it real: present the goal **visually with no text to copy**, and grade by **whether the generated code passes tests** instead of by an opinion about the prompt. This is objective, non-gameable, and teaches the actual professional feedback loop — *did my specification produce working software?*
- **Make** is the existing Project Task, with one addition: the student writes the test cases before the code. That's the verification artifact the research calls for, and it's what turns "I think it works" into "here's how I know."

### 3.3 Fading across the level

| Sessions | Predict | Modify | Specify | Make |
|---|---|---|---|---|
| 1–4 (foundations) | Heavy | Heavy | Light | Guided |
| 5–8 (building) | Medium | Medium | Heavy | Guided |
| 9–12 (independence) | Light | Light | Medium | **Mostly independent** |

By Session 12 the student should be doing something close to what the exit goal actually demands: given a goal, specify it, verify it, build it — with much less structure than Session 1 provided.

### 3.4 Add Lead-and-Reveal for the hardest concepts

For the two or three genuinely difficult moments in L1 (the game loop, collision math), don't hand over generated code at all. Use the technique that won the study: ask "what needs to happen first?" → reveal line 1 → "now what?" → reveal line 2. The existing DeepSeek integration can drive this. It produced the best learning-per-unit-friction of anything tested.

### 3.5 The exit assessment should be partly AI-free

Per the dual-assessment recommendation: if a student cannot **predict** and **trace** and **modify** a small piece of racing-game code without AI, they have not learned it, regardless of how good their prompts are. Session 12 should include a short AI-free component. This is also the only honest answer to "can they actually build a small web app now?"

## Part 4 — Why this is more efficient, not just more effective

The efficiency complaint is real and this addresses it directly:

- **Modes 1 and 2 cost nothing to grade** — no LLM call, no rubric prose to author. Just code and an expected output.
- **Mode 3 grades itself** by running tests — no `expectedConcepts` rubric to write per exercise, which is currently the most laborious authoring step and the source of most grading disputes.
- **Only Mode 4 needs teacher time**, which is where teacher judgment actually adds value.
- **Authoring gets cheaper too.** Writing a Predict exercise = a code snippet + its correct output. Writing a Specify exercise = a visual + test cases. Both are far faster to author (and far less arguable) than the current per-field rubric prose.
- Duplication drops out naturally: the four modes are genuinely different tasks, so there's no risk of an exercise accidentally duplicating the Project Task — the recurring problem in the current design.

---

## Part 5 — What I would pilot first

**Do not rebuild all of L1.** One capability milestone, one pilot, real students, then decide.

1. **Build Predict mode on Session 5 or 6** — cheapest to build (no LLM), highest-value missing piece, immediately tests whether students can actually read code.
2. **Convert two Specify exercises to test-case grading** — the platform already generates code and runs it; this needs test cases per exercise and a pass/fail check. Prove the objective-grading loop works before removing the subjective one.
3. **Then** decide on Modify/Parsons and the fading schedule based on what the first two reveal.

---

## Part 6 — Open questions for the teacher

1. **Visual goal presentation** for Specify mode requires an asset per exercise (a short clip or before/after of the game). Is that acceptable authoring cost, or should it be a rendered live demo the student can watch but not read code from?
2. **AI-free exit assessment** — does that fit the delivery model, or does it conflict with how sessions are run?
3. **Test-writing by students** (Mode 4) is a genuinely new skill not currently anywhere in L1. Does it belong in L1, or is it an L2/L3 concept that would overload a 12-year-old?
